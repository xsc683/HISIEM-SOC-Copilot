# 这个系统在解决什么问题

> **读者对象**：第一次接触本项目的人——安全工程师、后端工程师，或任何听过「AI SOC」但不确定它到底加在哪一层的人。
> **前置**：不需要读过本仓任何其它文档。只需要知道 SIEM 会出告警。

---

## 1. 先看一个具体场景

凌晨 3 点，HISIEM 弹出一条告警：

```text
SSH 暴力破解：来自 203.0.113.47 的 47 次失败登录
目标主机：web-prod-07
目标用户：svc-deploy
```

这条告警是**结构化的**：有规则、有实体、有时间窗、有风险分。但它没有回答分析师真正要回答的问题：

```text
攻击成功了吗？
如果成功，登录之后做了什么？
这个来源 IP 是什么来路？
应该怎么处置？
```

要回答这些，分析师要做的事是**手工**的：查相关日志、扩大时间窗、找失败之后有没有成功登录、查来源 IP 信誉、查主机那段时间的行为、翻 Runbook、对照 MITRE ATT&CK、写结论、建 Case。**每一步都要换一个系统、换一套查询语法、换一个上下文。**

问题的本质不是「告警不够准」，而是：**检测结果是结构化的，调查过程却完全是人工的。** 这件事重复、耗时、而且高度依赖经验。

---

## 2. 那为什么不干脆让模型来做？

因为安全调查的终点不是一段文字，而是**动作**：封 IP、禁用账号、隔离主机。一个能「自己动手」的 agent，一次提示注入或一次幻觉，就变成一个被禁用的账号或一台被隔离的生产主机。

所以本项目面对的问题其实是**两个**，而不是一个：

| 问题 | 如果只解决第一个会怎样 |
|---|---|
| 让调查自动化（读日志、取证据、形成判断） | 得到一个有用的助手 |
| 让这个助手**没有权限** | —— |
| 只解决第一个、不解决第二个 | 得到一个有用的、但会把生产环境搞坏的助手 |

本仓 README 把这句话写成了项目的核心主张：**一个 AI agent 可以在安全调查里真正有用，同时不被授予权限。** 凡是典型 agent demo 让模型「动手」的地方，这个系统插入一道边界。

---

## 3. 所以 Copilot 是什么

**HISIEM SOC Copilot 是决策层，不是第二个 SIEM，也不是第二个 SOAR。**

平台（HISIEM）继续拥有：安全事件采集、流式检测、告警、案件、**确定性的 SOAR 执行**，以及分析师用的 Web 控制台。Copilot 拥有的是：AI 调查、受治理的工具使用、证据组织、Finding 与 Verdict、响应提案，以及人工授权工作流。

| HISIEM 拥有 | Copilot 拥有 |
|---|---|
| 事件采集、流式检测 | AI 辅助调查 |
| 告警与运营数据 | 受治理的工具使用 |
| 案件管理 | 证据组织与知识上下文 |
| **确定性 SOAR 执行及其执行记录** | 响应**提案**与人工授权工作流 |
| 承载分析师 Web 应用 | 执行观察与工作区投影 |

（这张表的权威版本在根 `README.md` §17 与 `docs/architecture-overview.md` 图 8。）

一句话：**HISIEM 执行，Copilot 建议。**

---

## 4. 「只观察，不仲裁」

这是最容易讲错的一点。Copilot **不**是「第二个真相来源」。

- 它**不检测**：告警的产生是 HISIEM 的事。
- 它**不拥有告警数据**：Alert 只以引用（`ExternalResourceRef`）的形式出现在 Copilot 里，Copilot 从不复制一份。
- 它**不执行**：真正的动作在 HISIEM SOAR 里跑，执行器、凭据、动作实现都在 HISIEM 侧。
- 它**不判定执行结果**：**HISIEM 观察到的执行结果是唯一的最终执行真相**，而不是 Copilot「以为自己提交了什么」。

最后一条尤其重要。Copilot 会记录「我已经把命令交出去了」，但这句话**只说明交付动作发生了，不说明结果如何**。提交（submission）与执行（execution）在本系统里是**两台彼此独立的状态机**——`SUBMITTED` 不等于 `SUCCEEDED`。结果不确定时，系统进入一个显式的「需人工查看」状态，**绝不**靠假设把不确定折叠成某个终态。

这不是实现细节，而是产品的安全观：**一个调查助手不应该有权决定自己有没有成功。**

---

## 5. 核心链：Model proposes → Policy constrains → Human authorizes

这条链是产品的心脏。它把「谁有权做什么」拆成三个互不重叠的角色：

```text
模型提议   →   策略约束   →   人工授权
Model proposes → Policy constrains → Human authorizes
```

- **模型提议**：模型可以自主规划、自主选择读什么、自主形成判断。它的影响力**到「响应提案」为止**。
- **策略约束**：策略是一个**确定性函数**，不是模型的一部分。V1 只允许两种结果：`DENY`（无有效提案）或 `REQUIRE_APPROVAL`（必须人工决定）。**没有 `ALLOW_AUTOMATIC`**——低风险的写操作也一样不自动放行。
- **人工授权**：审批是一个**人**，不是一次策略判定。而且「批准」只是授权了**意图**，它本身不执行任何动作。

然后是链的后半段，把「授权」和「执行」也分开：

```text
持久命令记录意图  →  HISIEM 执行  →  Copilot 观察
Durable command records intent → HISIEM executes → Copilot observes
```

- **持久命令**：批准会在同一个事务里写入一条持久化的 outbox 事件。命令是幂等、可重试、可恢复的——重启不会产生第二份业务意图。
- **HISIEM 执行**：只有 HISIEM 有凭据和动作实现。
- **Copilot 观察**：Copilot 只保存执行引用与观察状态，并把它投影成分析师看得到的工作区。

**为什么这条链是核心？** 因为它把一个通常被糊在一起的问题拆开了：`工具结果 ≠ 证据`、`策略 ≠ 人工审批`、`人工审批 ≠ 执行`、`提交 ≠ 执行成功`、`遥测 ≠ 业务真相`。本仓 README §5 把这些写成九条彼此独立的区分，每一条都在代码里被强制、并被验收门覆盖。一个「看起来合理」的实现会把它们合并——这正是它们值得写下来的原因。

## 6. V1 只解决一件事

范围收得很紧：**Security Alert Investigation**。唯一入口是从 HISIEM 的 Alert 详情页发起调查，代表性场景是 SSH 暴力破解 → 可能账号失陷。

一次成功的调查产出的不是一段自然语言，而是**结构化结果**：Verdict、Confidence、Findings、Evidence、Uncertainties、ATT&CK 映射、响应建议。**每个关键 Finding 都必须能映射到具体 Evidence**；而且系统**必须允许 `INCONCLUSIVE`**——证据不足时给出「无法确定」，而不是被迫编一个确定判断。

「先有证据，再有结论」不只是流程约定，而是设计原则：**模型不能先形成结论再去找支持材料。**

---

## 7. 它明确不是什么

- 不是 SIEM，不是 SOAR（见上）。
- 不是聊天机器人，也不是通用安全问答。
- 不是自主 SOC：**没有任何一条路径能让模型授权一个动作**。
- 不是多 agent 系统：**故意只有一个调查 agent**。多 agent 不会让判断更可信，只会成倍放大权限面。
