# 一次调查的完整旅程

> **读者对象**：想知道「这套系统实际跑起来，一步接一步发生了什么」的人。适合已经读过 [`01-这个系统在解决什么问题.md`](01-这个系统在解决什么问题.md)，或已经知道「模型提议 → 策略约束 → 人工授权」这条链的人。
> **前置**：认识告警、日志、SOAR 这些基本概念即可，不需要读过任何代码。

下面用 V1 的代表性场景——**SSH 暴力破解 → 可能账号失陷**——从头走到尾。每一步都回答三件事：**谁做的、凭什么、失败会怎样（fail-closed 在哪）**。

---

## 第 1 步 · 告警产生，分析师发起调查

HISIEM 的检测规则命中，产生告警。Copilot 此刻**完全不知情**——它不订阅、不轮询、不检测，**告警的产生是平台的职责**。

分析师在 HISIEM 的告警详情页点「开始调查」。V1 的唯一主入口就是这里：**没有聊天入口、没有 Case 入口、没有手工 prompt 入口**。

**谁做的**：HISIEM 检测引擎；然后分析师（人）。
**凭什么**：检测规则的逻辑；分析师在 HISIEM 里已通过认证的会话。
**失败会怎样**：若该告警下已存在进行中的调查，用户应进入已有调查，**而不是**再创建一个——同一租户 + 同一告警，同一时刻**最多一个进行中的调查**。告警的产生与 Copilot 无关，它没有参与那条路径。

---

## 第 2 步 · 只传引用，Copilot 自己去取权威数据

启动请求**只带必要的身份上下文和告警引用**，然后 Copilot **重新从 HISIEM 获取权威告警数据**。这一步定义了整条信任边界的形状：**客户端声明什么，都不算事实**——Alert 内容、Tenant、Actor 身份、RBAC 权限、安全状态，**一律不得由客户端声明为权威事实**。租户和操作者身份来自**可信的服务端请求上下文**，永远不来自请求体，也永远不来自模型。

**谁做的**：Copilot 应用层 + HISIEM 适配器。
**凭什么**：服务间凭据 + HISIEM 服务端派生的 tenant / actor。
**失败会怎样（fail-closed）**：告警不存在或不可访问 → `FAILED`。**不得启动一次没有权威数据源的调查。**

---

## 第 3 步 · 调查被创建并运行，然后水合

Copilot 创建 Investigation，从 `CREATED` 走到 `RUNNING`。对外只有五个状态描述调查本身：

```text
CREATED → RUNNING → COMPLETED / FAILED / CANCELLED
```

内部运行阶段用另一套词表达（水合 → 规划 → 调查 → 验证 → 收尾）。**这些内部阶段、图节点、LLM 调用、工具调用都不进业务状态**——这让「调查处于什么业务阶段」不被运行时实现细节污染。

接着是**水合**：系统按调查持有的告警引用，取回权威告警上下文——规则、时间窗、来源/目标、用户、主机，以及告警里已有的有界关联事件。**这一步只建立调查上下文，不产生最终裁定。**

**谁做的**：系统的图（graph）**直接调用**，不是模型选择。
**凭什么**：调查持有的 `ExternalResourceRef`；`address_id` 必须来自该引用，**返回内容里的其它 ID 不得替换它**。
**失败会怎样（fail-closed）**：取不到权威上下文 → 调查走 `FAILED`。另外，告警里 HISIEM 侧的「分析师裁定」字段可读为上下文，但**不得映射为 Copilot 的 Verdict**——那是平台的判断，不是本次调查的结论。

---

## 第 4 步 · 规划

Copilot 形成一份**结构化**调查计划，典型步骤类似：验证检测模式 → 搜索相关活动 → 检查是否有成功认证 → 检查登录后行为 → 查询威胁情报 → 检索安全知识 → 评估失陷假设。计划可随新证据产生新 Revision。**V1 不允许用户直接编辑计划。**

**谁做的**：模型（提议）+ 应用层（落成结构化对象）。
**凭什么**：当前告警上下文。
**失败会怎样**：计划失败不致命——调查仍可在已有上下文上继续；真正决定终止与否的是后面的预算与证据充分性判断。

---

## 第 5 步 · 调查：模型在有界预算内选工具、取证据

这是**模型影响力最大**、也是边界最密的一步。模型能做的只有一件：**产生一个工具候选**——选哪个工具、带什么参数。仅此而已。

```text
模型工具候选
   ↓ Schema 校验
   ↓ 认证范围绑定（系统注入）
   ↓ 工具策略 / 预算校验
   ↓ 提供方适配器 → 类型化结果
   ↓ 证据归一化器 → 不可变 Evidence
```

**注意顺序**：策略与预算**在任何提供方调用之前**就先裁决——被拒绝的能力或已耗尽的预算**直接返回，根本不触及提供方**。

模型**不**直接调用提供方 SDK、HTTP 客户端、数据库或 Elasticsearch。模型参数里**禁止**出现 `tenant_id`、actor、角色、权限、授权头、服务凭据、提供方 base URL——这些由系统注入。

**谁做的**：模型选候选 → 系统绑定权限与范围 → 执行器校验策略与预算 → 适配器取数据。
**凭什么**：模型的调查需要；但**权限始终由系统绑定，不由模型声明**。
**失败会怎样（fail-closed，本步最密集）**：
- **类型化失败不产生证据。** 失败、空结果、未落地的调用**都不能被洗成事实**——专防「假成功证据」：一个坏掉的调用返回空结果，而 agent 的证据看起来仍然「有据可依」。
- 结果过大是 `RESULT_TOO_LARGE`，**绝不静默截断**。
- 所有远端内容都是**不可信数据**，包括那些看起来像指令的文本。
- **租户**由服务端注入；模型提供的租户字段被拒绝。

关于「模型到底能选哪几个工具」，见 [`03-为什么-Agent-不能自己授权.md`](03-为什么-Agent-不能自己授权.md)。

---

## 第 6 步 · 证据归一化：工具结果不是证据

原始工具返回值是**数据**，不是事实，必须经过归一化才成为证据：

```text
类型化 ToolResult → 归一化器 → 去重 → 记录证据批次 → 不可变 Evidence
```

归一化器负责：挑出有界观察、附上溯源（provenance）、附上采集时间、生成原始引用、计算内容哈希与去重键、剔除提供方噪声。**模型不能自己设置**证据的溯源、来源工具调用 id、采集时间或资源权威性。

**谁做的**：系统（归一化器）。**凭什么**：类型化工具结果 + 系统已知的调用上下文。
**失败会怎样**：没有结果 → 没有证据；归一化不通过 → 没有证据。**证据不是模型说的，是系统从真实结果里落下来的。**

---

## 第 7 步 · 假设评估

模型围绕明确的 Hypothesis 调查，每个假设随证据被更新为：

```text
OPEN / SUPPORTED / CONTRADICTED / UNRESOLVED
```

证据不够就继续调查；证据够了、或触发终止条件，就产出调查结果。

**谁做的**：模型（评估）+ 系统（记录）。**凭什么**：已落地的证据。
**失败会怎样**：证据冲突时**保留冲突的证据**，并在结果里产生一条 Uncertainty——不是抹平冲突，而是把冲突写下来。

---

## 第 8 步 · 调查结果与裁定

最终结果是结构化对象，至少包含 Verdict、Confidence、Findings、Evidence、Uncertainties、ATT&CK 映射、响应建议。两条硬性质：**关键 Finding 必须引用 Evidence**；**系统必须允许 `INCONCLUSIVE`**，不得强制产生确定判断。

**`FAILED` 与 `INCONCLUSIVE` 是两件不同的事**：

```text
FAILED        = 系统没有完成一次有效调查
INCONCLUSIVE  = 调查正常完成了，但证据不足以产生确定判断
```

因此下面这种组合完全合法，而且是被**鼓励**的：

```text
Investigation.status = COMPLETED
Verdict              = INCONCLUSIVE
```

预算耗尽、部分数据源不可用、证据冲突——这些情况**优先产生有效的 INCONCLUSIVE 结果，而不是 FAILED**。理由是产品性的：一次「我查了但无法确定」是**有价值的交付物**；把它变成「系统坏了」，等于丢掉调查已经获得的一切。

**谁做的**：模型（判断）+ 领域层（不变量）。**凭什么**：证据链。
**失败会怎样**：致命失败 → `FAILED`；预算耗尽 → 先停下、保留已有证据，再产出 `COMPLETED + INCONCLUSIVE`。

---

## 第 9 步 · 响应提案

**只有调查到达 `COMPLETED` 之后**，如果确实需要响应，才会开始一条**独立于调查生命周期的**提案工作流。这一点很关键：**提案、审批、提交、执行观察，全程都不改变 `Investigation.status`。** 一次「调查做完了、但响应被驳回」的历史，不会让那次调查本身变成失败的调查。

提案必须引用支持其必要性的证据。浏览器提交的是**有界契约**（动作键、证据 id、参数、理由），**执行目标由服务端依据已持久化的调查来源告警引用推导**——浏览器不得提交提供方、资源类型、地址 id、租户、actor 等越界字段。越界字段**显式拒绝**（不是静默丢弃）。SOAR Playbook 只能从已发布且启用的下拉列表里选，**不接受自由文本**。

**谁做的**：模型/应用层形成提案对象；人（或前端）提交有界提案。**凭什么**：调查结果 + 证据引用。
**失败会怎样（fail-closed）**：越界字段 → 拒绝；没有证据支持的提案不能进入执行路径。

---

## 第 10 步 · 策略裁决

V1 只有两种结果：

```text
DENY               → 不产生可派发的命令
REQUIRE_APPROVAL   → 进入人工审批
```

**没有 `ALLOW_AUTOMATIC`**，V1 不提供「低风险写操作自动放行」。而且**人工审批不能替代策略校验**：一个无效提案必须被策略直接 `DENY`，不能靠人工点一下来「洗白」。

**谁做的**：确定性策略函数。**凭什么**：提案内容。
**失败会怎样（fail-closed）**：非法提案 → `DENY`，执行路径到此为止。

---

## 第 11 步 · 人工授权

需要审批的提案进入 `WAITING_APPROVAL`——**注意这个状态属于提案聚合，不属于调查状态**。核心约束：

- **审批绑定到精确的提案版本与内容哈希。** 一个过期的审批**不能**授权已经改变了的意图（这就是 TOCTOU 防护）。
- **决策恰好一次**；审批人必须已认证且有审批权限；**模型永远不能产生审批决策**。
- **审批这个 HTTP 请求本身不执行任何响应。** 它在事务内只做四件事：持久化不可变的审批决策、把提案从 `WAITING_APPROVAL` 迁到 `APPROVED`、持久化一个 `response_execution_queued` 领域事件、原子写入持久化 outbox。**它不调用 SOAR，也不创建执行引用。**

**谁做的**：人。**凭什么**：已认证身份 + 审批权限 + 提案版本/哈希匹配。
**失败会怎样（fail-closed）**：**驳回不产生可派发的命令**，提案进入 `REJECTED`，且**不改变已经形成的调查结果**。审计角色对整条响应流程只读。

---

## 第 12 步 · 持久提交

真正的提交由独立的 outbox worker 稍后完成，携带稳定的幂等键。两个职责分离的目的地：

```text
response.execution.submit   → 提交 worker：只负责在一次提交中取得真实执行 id
response.execution.observe  → 观察 / 对账 worker：只推进一个已经提交的执行
```

**谁做的**：持久执行 dispatcher + 提交 runner。**凭什么**：幂等键（一个租户 + 一个提案 = 一个逻辑意图）+ 有界重试（有界次数、有界退避）。
**失败会怎样（fail-closed，这一步最微妙）**：
- 提交状态与执行状态是**两台独立状态机**：`SUBMITTED` **不说明**结果如何。
- 结果**不确定**时进入 `ATTENTION_REQUIRED`——一个**显式的「不确定」状态，人必须去看**，**绝不**被折叠成终态。
- **一次不确定的提交永远不会变成 `SUCCEEDED` 或 `FAILED`**（靠假设变出来的终态是伪造的）。
- **重试永远不产生第二份业务意图**；重启或恢复也不产生重复意图。
- 提供方返回的合法非终态（例如「运行中」）**不是失败**：应通过持久化延迟观察推进，**绝不允许靠耗尽重试次数把它逼成死信**。

---

## 第 13 步 · HISIEM 执行，Copilot 观察

HISIEM SOAR 执行。执行器、凭据、动作实现**都在 HISIEM 侧**；Copilot 只保存持久化提交意图、执行引用投影与审计事实。**HISIEM 不会回调 Copilot 获取授权。**

Copilot 通过观察 worker 推进执行状态，直到 HISIEM 观察到一个终态结果。**HISIEM 观察到的执行结果，是唯一的最终执行真相。**

```text
Investigation Result      = 调查是否完成、安全判断是什么
Response Execution Result = 批准后的响应是否成功执行
```

两者**必须独立**。因此下面这种组合是允许的，而且必须被如实展示：

```text
Investigation: COMPLETED   Verdict: MALICIOUS
Response Execution: FAILED
```

**谁做的**：HISIEM SOAR（执行）+ 系统（观察）。**凭什么**：HISIEM 自己的执行模型与返回的执行观察。
**失败会怎样（fail-closed）**：执行失败**不改变调查结果**；结果不确定 → 停在 `ATTENTION_REQUIRED` 等人，**不会假设成功，也不会假设失败**。

---

## 第 14 步 · 工作区投影

分析师在工作区里看到的，是**从持久化状态重建出来的投影**，不是一个缓存：

- 保留权威区分：知识上下文**绝不**被渲染成平台事实；agent 裁定**绝不**被渲染成分析师的裁定。
- **服务端真相在刷新时获胜**：陈旧的客户端快照会被更新的服务端状态覆盖。
- **不发明任何东西**：持久化生命周期没有记录的审批、执行、提交状态，界面上不出现。
- **绝不渲染内部**：思维链、prompt、图检查点都不展示。

**谁做的**：HISIEM 仓库里的前端（**本仓不含前端**）。**凭什么**：Copilot 的工作区投影契约。
**失败会怎样**：客户端与服务器不一致时，**服务器赢**。
