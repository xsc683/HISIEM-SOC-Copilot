## 1. 先分清三层，别跳层

这个仓的文档不是平铺的，它有**三种性质完全不同的层**。跳层读是新手最常踩的坑。

| 层 | 是什么 | 该怎么读 |
|---|---|---|
| **学习层** | 本目录 `docs/guide/` —— 从哪进门 | 先读，一次读完 |
| **权威契约层** | 描述**当前**行为、并且**实现必须服从**它 | 按问题查，是你要找的答案所在 |
| **取证层 / 工程史层** | 代码级分析、验收证据、冻结规格 | **不是入门材料**。只在你要核证某个论断时读 |

一个具体的提醒：本仓文档里出现的 **「Stage A–E」「E1-C2」这类词是内部工程史术语，不是产品模型**（`docs/stage-reports/index.md` 与 `docs/stage-contracts/README.md` 都明文写了这一点）。**入门阶段请忽略它们**，它们只在第四层有意义。

## 4. 三个「非入门」集合：定位与先后关系

这三个集合**不是**用来入门的。它们各自的用途和阅读时机完全不同。

### `docs/architecture-analysis/` —— 代码级取证集

| 项 | 内容 |
|---|---|
| 是什么 | 9 篇（00–08）**对实际源码取证**的分析文档，关键结论都带 `file:line` 相对路径证据；共 6571 行、38 张 mermaid 图 |
| 覆盖 | 00 分层与包边界 · 01 端到端关键数据流 · 02 领域模型与编排 · 03 工具执行策略与 Provider · 04 证据归一化与响应闭环 · 05 应用层与 API · 06 知识库与威胁情报 · 07 持久化可靠性与可观测 · 08 评估体系 |
| 代码基线 | 分支 `capability-mcp` @ `1e567be`，生成于 2026-09-22 |
| **什么时候读** | **当你已经读过对应主题的权威契约、想验证「代码里到底是不是这样」的时候。** |
| **什么时候不要读** | 不要用它替代入门。它是**取证**，不是讲解；它假设你已经知道要找什么。 |

**先后关系**：**契约在前，取证在后。** 先读权威契约知道「规矩是什么」，再用这 9 篇去核「代码有没有照做、做在哪一行」。

### `docs/stage-reports/` —— 工程史的**输出**（验收证据）

| 项 | 内容 |
|---|---|
| 是什么 | 工程过程的**验证记录**：每一个阶段建了什么、跑了什么、什么通过了、什么留了开口 |
| 建议入口 | `docs/stage-reports/index.md` —— 有阅读顺序和**汇总的已知项登记表** |
| **只读两篇的话** | **E1** 报告（验收模型是怎么设计的）与 **E7** 封存报告（完整最终验证 + 诚实的未决清单） |
| **什么时候读** | 当你想知道**某个论断背后的证据**时。 |
| **注意** | 这里的术语是内部工程史，**不是产品模型**；读它是为了证据，不是为了介绍。 |

### `docs/stage-contracts/` —— 工程史的**输入**（冻结规格）

| 项 | 内容 |
|---|---|
| 是什么 | 冻结的四平面 v1.0 契约、阶段实施规格、以及执行 prompt——即 `stage-reports/` 这些**输出**所对应的**输入** |
| 状态 | **冻结的工程史**，不是产品模型 |
| **关键规则** | `00_Four-Plane_Architecture_Contract_Freeze.md` 是 **2026-09-14 的 v1.0 基线**；**它和代码不一致时，代码赢** |
| **什么时候读** | 只有当你需要追溯「当初是照着什么规格做的」时才读。 |

**三者的先后关系一句话**：

```text
权威契约（当前行为）
   ↓ 想核证
architecture-analysis/（代码取证）
   ↓ 想知道证据
stage-reports/（验收输出）
   ↓ 想知道当初照着什么做的
stage-contracts/（冻结输入）
```

**入门阶段一个都不需要读。** 它们的价值在「核证」，不在「入门」。

## 5. 关于「哪份说了算」

文档之间出现分歧时，判断顺序是：

```text
代码  >  权威契约文档  >  冻结规格（stage-contracts）  >  工程史叙述（stage-reports）
```

- `docs/README.md` 明确写了：架构与持久化文档是**权威**，实现服从它们，且 `tests/architecture/` **机械地**强制分层规则。
- `docs/stage-contracts/README.md` 明确写了：冻结基线与代码不一致时，**代码赢**。
- 一个**已记录、未修正**的例子：`docs/stage-reports/STAGE_E_E3_...md` 引用了一份**并不存在**的文件（`06_Stage-E_XP-01_Cross-Plane_Evaluation_Pack.md`，实际文件名是 `06_Stage-E_Detailed_Design.md`）。`stage-contracts/README.md` 说明这是**命名笔误而非缺失文档**，并刻意保留原样，因为那份报告本身是证据。
- **本文档集自己**也记录了一处：见 [`03-为什么-Agent-不能自己授权.md`](03-为什么-Agent-不能自己授权.md) §2 关于「4 个还是 6 个工具」的核对。

**想知道这类「已知的诚实缺口」的完整清单**：根 `README.md` §18 与 `docs/stage-reports/index.md` 的「已知非阻塞项」表。

## 6. 一份可直接照做的阅读计划

```text
第 1 天（入门，约 1 小时）
  根 README.md
  docs/architecture-overview.md（只看 8 张图和表）
  docs/guide/01 → 02 → 03

第 2 天（打地基，约 2 小时）
  docs/domain-model.md（导言 + 聚合清单 + §25–§27 + 状态机）
  docs/v1-user-flow-and-scope.md

第 3 天起（按需，不要贪多）
  想查什么，回到本文 §3 的表
  要核证，才进 architecture-analysis/
  要证据，才进 stage-reports/
```

**最后一个建议**：这个仓的文档写得比一般项目「重」，因为它的规矩多。但规矩多不等于要先读完。**先能用一句话说清「模型提议 → 策略约束 → 人工授权」，再往下钻**——其余所有细节都是这句话的展开。
